**שדה גלואה GF(2^8)**

כל האריתמטיקה של Reed-Solomon מתבצעת בתוך שדה גלואה. כדי להבין למה, צריך להבין תחילה מה הבעיה עם כפל בתים רגיל.

**הבעיה: כפל בתים שוברת את הטווח**

בית הוא ערך בין 0 ל-255. כשכופלים שני בתים בחשבון רגיל, התוצאה יכולה להגיע עד 65025, מספר בן 16 ביט. נדרש מנגנון שמחזיר את התוצאה לטווח 0-255.

**ניסיון ראשון: מודולו 256**

גישה אחת היא לקחת רק את 8 הביטים התחתונים של התוצאה:

$$a \times b \pmod{256}$$

הבעיה: זה שובר את היכולת לבצע חילוק. לדוגמה:

$$2 \times 128 = 256 \equiv 0 \pmod{256}$$

קיבלנו אפס. כלומר כפל של שני ערכים שאינם אפס נותן אפס, מה שהופך חילוק לבלתי אפשרי. אם 2 כפול 128 מתאפס, אין משמעות לשאלה "128 חלקי 2". ל-Reed-Solomon נדרש חילוק, לכן מודולו 256 לא מתאים.

**הפתרון: ייצוג בתים כפולינומים**

במקום לחשוב על בית כמספר שלם, מפרשים את 8 ביטיו כמקדמים של פולינום מדרגה 7. המקדמים הם 0 או 1 בלבד. לדוגמה:

$$0\text{b}10110011 = x^7 + x^5 + x^4 + x + 1$$

חיבור של שני פולינומים כאלה מתבצע על ידי חיבור מקדמים תואמים מודולו 2, כלומר ללא נשא. התוצאה זהה לחלוטין ל-XOR ביטוני:

$$0+0=0 \qquad 0+1=1 \qquad 1+0=1 \qquad 1+1=0$$

**כפל: מדוע הפולינום הפרימיטיבי?**

כפל שני פולינומים בני 8 ביטים יכול לתת פולינום מדרגה עד 14, שמייצג יותר מ-8 ביטים. כדי לצמצם חזרה ל-8 ביטים לוקחים את תוצאת הכפל מודולו פולינום אי-פריק מדרגה 8. בפרויקט זה:

$$p(x) = x^8 + x^4 + x^3 + x^2 + 1$$

"אי-פריק" פירושו שאי אפשר לפרק אותו לגורמים של פולינומים קטנים יותר מעל GF(2), בדומה למספר ראשוני שאי אפשר לפרק לגורמים שלמים. תכונה זו מבטיחה שלכל ערך שאינו אפס קיים הופכי כפלי, כלומר חילוק תמיד מוגדר.

**האלגוריתם הקונקרטי לכפל**

בפועל לא בונים פולינומים מפורשים. מבצעים את הכפל ביטונית. הפעולה הבסיסית היא כפל בית אחד ב-2:

```
fn gf_mul2(a: u8) -> u8:
    msb = (a & 0x80) != 0      // האם הביט הגבוה דלוק
    result = a << 1             // שיפט שמאלה = כפל ב-x
    if msb:
        result ^= 0x11D         // הפחתת p(x) מודולו
    return result
```

למה XOR עם 0x11D? כשה-MSB דלוק לפני השיפט, הפולינום לאחר השיפט עולה מדרגה 8 וחורג מ-8 ביטים. צריך להפחית את p(x). הפחתה ב-GF(2) היא XOR, ולכן מבצעים XOR עם 0x11D שמייצג את p(x). בפועל ביט x^8 (הביט ה-9) אבד ב-overflow של ה-u8, כך ש-XOR עם 0x11D שקול ל-XOR עם הביטים התחתונים בלבד, אך משתמשים ב-0x11D כדי להישאר נאמנים לייצוג הפולינום המלא.

דוגמה: 0b10000000 כפול 2

1. MSB דלוק, מבצעים שיפט שמאלה: 0b100000000 (9 ביטים)
2. XOR עם 0x11D: 0b100000000 XOR 0b100011101 = 0b000011101
3. התוצאה: 0b00011101 = 29

לכפל בית שרירותי מפרקים אותו לביטיו ומפעילים gf_mul2 בחזקות עולות, תוך XOR של התרומות הרלוונטיות.

| ערך קלט | MSB דלוק? | לאחר שיפט | לאחר XOR עם 0x11D | תוצאה |
|----------|-----------|------------|-------------------|--------|
| 0b00000011 (3) | לא | 0b00000110 | -- | 6 |
| 0b10000000 (128) | כן | 0b100000000 | XOR 0b100011101 | 29 |
| 0b10110001 (177) | כן | 0b101100010 | XOR 0b100011101 | 111 |

**טבלאות EXP ו-LOG לכפל מהיר**

הגנרטור 2 הוא שורש פרימיטיבי של GF(2^8): חזקותיו 2^0, 2^1, ..., 2^254 עוברות על כל 255 הערכים השונים מאפס בשדה, ואז 2^255 = 1 ומתחילות מחדש. זה מאפשר לבנות שתי טבלאות:

- EXP_TABLE: הערך ה-GF של 2 בחזקת i, עבור כל i
- LOG_TABLE: ה-i שעבורו 2^i שווה לערך נתון

**[תמונה: תרשים מעגלי המציג את 255 הערכים של GF(2^8) מסודרים בעיגול, עם חץ המראה את הרצף 2^0 -> 2^1 -> ... -> 2^254 -> 2^0, ממחיש שהגנרטור עובר על כל ערך בדיוק פעם אחת לפני שחוזר להתחלה]**

| i | EXP_TABLE[i] | LOG_TABLE[EXP_TABLE[i]] |
|---|-------------|--------------------------|
| 0 | 1 | 0 |
| 1 | 2 | 1 |
| 2 | 4 | 2 |
| 3 | 8 | 3 |
| 4 | 16 | 4 |
| 5 | 32 | 5 |

לכפל שני ערכים משתמשים בזהות הלוגריתמית. חיבור המעריכים מתבצע מודולו 255:

$$a \times b = \text{EXP\_TABLE}\left[(\text{LOG\_TABLE}[a] + \text{LOG\_TABLE}[b]) \bmod 255\right]$$

לחילוק מחסירים את המעריכים:

$$a \div b = \text{EXP\_TABLE}\left[(\text{LOG\_TABLE}[a] - \text{LOG\_TABLE}[b] + 255) \bmod 255\right]$$

דוגמה: 4 כפול 8. LOG_TABLE[4] = 2, LOG_TABLE[8] = 3, סכום המעריכים הוא 5, EXP_TABLE[5] = 32. התוצאה זהה לחשבון רגיל כי לא חצינו את גבול 255. לעומת זאת 200 כפול 200 בחשבון רגיל הוא 40000, ואילו ב-GF סכום המעריכים מחזיר ערך בין 0 ל-254 ו-EXP_TABLE נותן בית תקין.
