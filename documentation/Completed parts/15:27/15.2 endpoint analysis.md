### 15.2 הצגת מקרה (Use Case) עבור כל הפונקציות העיקריות בפרויקט

---

#### UC-01: רישום משתמש

| שדה | ערך |
|-----|-----|
| **תיאור** | משתמש חדש יוצר חשבון במערכת |
| **שחקנים** | משתמש לא מזוהה |
| **תנאי קדם** | המשתמש אינו מחובר למערכת |
| **תנאי יציאה** | המשתמש מחובר עם זוג טוקנים תקין |

**זרימה ראשית:**
1. המשתמש שולח שם משתמש, כתובת מייל, סיסמה ופרטים אישיים.
2. שירות האימות מגבב את הסיסמה באמצעות Argon2 ויוצר רשומת אימות.
3. שירות האימות יוצר פרופיל משתמש בשירות המשתמשים.
4. המערכת מנפיקה access token ו-refresh token ומחזירה אותם למשתמש.

**זרימות חלופיות:**
- אם שם המשתמש או המייל כבר קיימים - 409 Conflict.
- אם יצירת הפרופיל בשירות המשתמשים נכשלת - רשומת האימות נמחקת אוטומטית (saga) ומוחזרת שגיאה.

#### UC-02: התחברות

| שדה | ערך |
|-----|-----|
| **תיאור** | משתמש קיים מתחבר למערכת |
| **שחקנים** | משתמש לא מזוהה |
| **תנאי קדם** | קיימת רשומת משתמש פעילה |
| **תנאי יציאה** | המשתמש מחובר עם זוג טוקנים תקין |

**זרימה ראשית:**
1. המשתמש שולח שם משתמש או מייל, סיסמה ומידע על המכשיר (device_info).
2. שירות האימות מאמת את הסיסמה מול הגיבוב השמור.
3. המערכת מנפיקה access token ו-refresh token עם device_info המשויך ומחזירה אותם.

**זרימות חלופיות:**
- אם פרטי ההתחברות שגויים - 401 Unauthorized.
- אם החשבון מושעה - 403 Forbidden.

#### UC-03: רענון טוקן

| שדה | ערך |
|-----|-----|
| **תיאור** | access token פג תוקף והמשתמש מבקש זוג חדש |
| **שחקנים** | משתמש מזוהה |
| **תנאי קדם** | refresh token תקין ולא בוטל שמור ב-cookie |
| **תנאי יציאה** | המשתמש מחזיק זוג טוקנים חדש; הטוקן הישן בטל |

**זרימה ראשית:**
1. הלקוח שולח בקשה עם ה-refresh token מה-cookie.
2. שירות האימות מאמת את הטוקן מול מסד הנתונים.
3. הטוקן הישן מבוטל ומונפק זוג חדש (token rotation).

**זרימות חלופיות:**
- אם הטוקן לא קיים, פג תוקפו, או בוטל - 401 Unauthorized.

#### UC-08: העלאת קובץ

| שדה | ערך |
|-----|-----|
| **תיאור** | משתמש מעלה קובץ וידאו למערכת בתהליך multipart |
| **שחקנים** | משתמש מזוהה |
| **תנאי קדם** | המשתמש מחובר |
| **תנאי יציאה** | הקובץ שמור ב-MinIO ורשומתו קיימת במסד הנתונים ושייכת למשתמש |

**זרימה ראשית:**
1. הלקוח שולח בקשת initiate עם שם הקובץ - המערכת מחזירה מזהה העלאה ומזהה קובץ.
2. הלקוח שולח את תוכן הקובץ ב-chunks של עד 20MB כל אחד, כל אחד עם מזהה ההעלאה.
3. הלקוח שולח בקשת complete - שירות הקבצים מאחד את כל ה-chunks ב-MinIO.
4. 2MB הראשונים של הקובץ נבדקים לאימות codec. קובץ המכיל H.264, HEVC, VP9, VP8, AV1 או MPEG4 מסומן כ-carrier.

**זרימות חלופיות:**
- אם הקובץ אינו וידאו תקין - הקובץ נשמר ללא סימון carrier.

#### UC-13: הטמעת מידע בווידאו

| שדה | ערך |
|-----|-----|
| **תיאור** | משתמש מטמיע קובץ נסתר בתוך קובץ וידאו נשא |
| **שחקנים** | משתמש מזוהה |
| **תנאי קדם** | שני הקבצים קיימים ושייכים למשתמש; קובץ הנשא מסומן כ-carrier |
| **תנאי יציאה** | קובץ וידאו חדש עם המידע המוטמע שמור במערכת ושייך למשתמש |

**זרימה ראשית:**
1. הלקוח שולח בקשה עם מזהה קובץ הנשא, מזהה הקובץ להטמעה ופרמטרי הטמעה.
2. שירות הסטגנוגרפיה מוריד את שני הקבצים במקביל.
3. המטען עובר קידוד Reed-Solomon להוספת יכולת תיקון שגיאות.
4. 64 ביט כותרת מוטמעים ראשונים.
5. FFmpeg מפרק לפריימים; רק I-frames מעובדים.
6. כל פריים מחולק לבלוקים, DCT מוחל, הביטים מוטמעים, IDCT מחזיר לפיקסלים.
7. FFmpeg מקודד לקובץ H.264 חדש ב-CRF 23.
8. הקובץ המוטמע מועלה ומסומן כ-steg object.

**זרימות חלופיות:**
- אם המטען גדול מדי להכיל בנשא - שגיאה לפני תחילת העיבוד.

#### UC-14: חילוץ מידע מווידאו

| שדה | ערך |
|-----|-----|
| **תיאור** | משתמש מחלץ קובץ נסתר מתוך קובץ וידאו מוטמע |
| **שחקנים** | משתמש מזוהה |
| **תנאי קדם** | הקובץ קיים, שייך למשתמש ומסומן כ-steg object |
| **תנאי יציאה** | קובץ המטען המקורי הגיע ללקוח |

**זרימה ראשית:**
1. הלקוח שולח בקשה עם מזהה הקובץ ופרמטרי חילוץ התואמים להטמעה המקורית.
2. FFmpeg מפרק לפריימים; רק I-frames מעובדים.
3. 64 ביט ראשונים מפוענחים לגודל המטען.
4. הביטים מחולצים עד להשגת הגודל המצופה.
5. Reed-Solomon מתקן שגיאות ומשחזר את המטען.

**זרימות חלופיות:**
- אם הפרמטרים אינם תואמים לאלו שבהם הוטמע - ייחלצו בתים שגויים.
