## 15.12 תיאור הרכיבים המוצעים

המערכת מורכבת משישה שירותי backend ו-frontend אחד. כל שירות הוא יחידה עצמאית עם בסיס נתונים נפרד, מכיל לוגיקה ספציפית לתחום אחריותו, ומתקשר עם שירותים אחרים אך ורק דרך HTTP. הרכיבים לפי סדר זרימת הנתונים:

| שירות | פורט | תחום אחריות |
|---|---|---|
| Frontend | — | ממשק משתמש, ניהול מצב אימות |
| API Gateway | 3000 | נקודת כניסה יחידה, ניתוב לשירותים |
| Eureka Service | 3005 | גילוי שירותים, הפצת מפתחות JWT |
| Auth Service | 3001 | אימות, הנפקת JWT, ניהול refresh tokens |
| User Service | 3002 | פרופילי משתמשים, אימות פרטי כניסה |
| Files Service | 3004 | אחסון קבצים, גילוי קודק, ניהול מטא-נתונים |
| Steganography Service | 3003 | הטמעת וחילוץ מידע חבוי בווידאו |

---

### API Gateway

#### 15.12.1 תפקיד
פרוקסי שקוף לחלוטין — נקודת הכניסה היחידה של המערכת. מנתב בקשות לשירות המתאים לפי קידומת הנתיב, מסיר את `/api` ומעביר הכל הלאה כולל הכותרות וגוף הבקשה.

#### 15.12.2 קלטים
| מקור | נתון |
|---|---|
| לקוח (דפדפן) | כל בקשות HTTP של המשתמש — method, headers, גוף הבקשה כ-stream |
| auth_service | תגובת HTTP — status code, headers (כולל Set-Cookie), גוף התגובה כ-stream |
| user_service | תגובת HTTP — status code, headers, גוף התגובה כ-stream |
| files_service | תגובת HTTP — status code, headers, גוף התגובה כ-stream (כולל זרמי קבצים) |
| steganography_service | תגובת HTTP — status code, headers, גוף התגובה כ-stream |
| Eureka | כתובות URL של כל השירותים הרשומים (נטענות בזמן אתחול, מתעדכנות ב-RwLock) |

#### 15.12.3 פלטים
| יעד | נתון |
|---|---|
| auth_service | בקשות `/auth/*` (מסיר קידומת `/api`) |
| user_service | בקשות `/users/*` |
| files_service | בקשות `/files/*` |
| steganography_service | בקשות `/embed/*` ו-`/extract/*` |
| לקוח | תגובת השירות המשוחזרת כולל CORS headers, או 503 אם השירות אינו רשום ב-Eureka |
| Eureka (בזמן אתחול) | `POST /register {service_name, service_url}` |
| Eureka (כל 30 שניות) | `GET /config/api_gateway` — רענון תקופתי |
| Eureka (כל 30 שניות) | `POST /heartbeat {service_name}` |

### Eureka Service

#### 15.12.1 תפקיד
מרשם שירותים ומרכז קונפיגורציה. שומר את מפתחות ה-JWT, משכי טוקן, וכתובות כל השירותים הרשומים. כל שירות נרשם אצלו בזמן אתחול וטוען ממנו את הגדרות הסביבה שלו.

#### 15.12.2 קלטים
| מקור | נתון |
|---|---|
| כל שירות (בזמן אתחול) | `POST /register {service_name, service_url}` — רישום ראשוני |
| כל שירות (בזמן אתחול) | `GET /config/{service_name}` — טעינת קונפיגורציה ראשונית (עם retry עד 10 פעמים, 2 שניות בין ניסיון) |
| כל שירות (כל 30 שניות) | `GET /config/{service_name}` — רענון תקופתי של הקונפיגורציה |
| כל שירות (כל 30 שניות) | `POST /heartbeat {service_name}` — אות חיים |

#### 15.12.3 פלטים
| יעד | נתון |
|---|---|
| auth_service | `ConfigResponse` הכולל jwt_public_key, jwt_private_key, jwt_durations, services map |
| כל שירות אחר | `ConfigResponse` ללא jwt_private_key (שדה זה מוחזר רק לשירות המאמת) |

### Auth Service

#### 15.12.1 תפקיד
ניהול מחזור חיי הזהות: הרשמה (saga), התחברות, רענון טוקן, התנתקות. השירות היחיד המחזיק את מפתח ה-RSA הפרטי לחתימת JWT.

#### 15.12.2 קלטים
| מקור | נתון |
|---|---|
| לקוח (דרך gateway) | `POST /auth/register {username, email, password, ...}` |
| לקוח (דרך gateway) | `POST /auth/login {email/username, password, device_info}` |
| לקוח (דרך gateway) | `POST /auth/refresh` עם Cookie: refresh_token |
| לקוח (דרך gateway) | `POST /auth/logout` |
| Eureka (בזמן אתחול) | jwt_private_key, jwt_public_key, user_service_url, access_dur, refresh_dur |
| Eureka (כל 30 שניות) | רענון תקופתי של הקונפיגורציה — עדכון כתובת user_service ומפתחות |
| Auth DB | טבלת `user_roles` — תפקידי המשתמש |
| Auth DB | טבלת `refresh_tokens` — token_hash, expires_at, device_info |

#### 15.12.3 פלטים
| יעד | נתון |
|---|---|
| לקוח | `LoginResponse {user, access_token}` + Set-Cookie: refresh_token (HttpOnly) |
| לקוח | `RefreshTokenResponse {access_token}` + Set-Cookie חדש |
| user_service | `POST /users` — יצירת פרופיל משתמש |
| user_service | `POST /internal/auth/verify-credentials` — אימות סיסמה |
| user_service | `DELETE /users/{id}` — מחיקת פיצוי (saga compensation, עד 3 ניסיונות) |
| Auth DB | INSERT/DELETE `refresh_tokens`, SELECT `user_roles` |
| Auth DB | DELETE expired `refresh_tokens` (background cleanup כל 60 דקות) |

### User Service

#### 15.12.1 תפקיד
ניהול פרופילי משתמשים. CRUD על נתוני המשתמש. מספק נתיב פנימי לאימות פרטי כניסה עבור auth_service.

#### 15.12.2 קלטים
| מקור | נתון |
|---|---|
| auth_service (פנימי) | `POST /users {username, email, password_hash, ...}` — יצירת משתמש |
| auth_service (פנימי) | `DELETE /users/{id}` — מחיקת compensation |
| auth_service (פנימי) | `POST /internal/auth/verify-credentials {email, password}` |
| לקוח (דרך gateway) | `GET /users/{id}`, `GET /users/me`, `PATCH /users/me`, `PATCH /users/{id}` — קריאה ועדכון פרופיל |
| Eureka | jwt_public_key לאימות JWT על נתיבי הלקוח |
| User DB | טבלת `users` |

#### 15.12.3 פלטים
| יעד | נתון |
|---|---|
| auth_service | `UserResponse {id, username, email, ...}` — בעת יצירה ואימות |
| לקוח | `UserResponse` |
| User DB | INSERT / UPDATE / DELETE `users` |

### Files Service

#### 15.12.1 תפקיד
שכבת הפשטה מעל MinIO. מנהל העלאות multipart בשלושה שלבים, הורדות, ומטא-נתוני קבצים. מבצע גילוי קודק אוטומטי לזיהוי carrier videos.

#### 15.12.2 קלטים
| מקור | נתון |
|---|---|
| לקוח (דרך gateway) | `POST /files/initiate`, `POST /files/upload-chunk`, `POST /files/complete` — העלאת קובץ |
| לקוח (דרך gateway) | `GET /files`, `GET /files/{id}/download`, `PUT /files/{id}` |
| steganography_service (פנימי) | אותם נתיבי העלאה עם טוקן המשתמש |
| steganography_service (פנימי) | `PATCH /internal/files/{id}/embedded` — סימון is_steg_object |
| JWT Bearer token | בכל בקשה — אימות ושליפת user_id |
| MinIO | bytes של קובץ בהורדה, ETag בהעלאה, 2MB ראשונים לגילוי קודק |
| Files DB | טבלת `files` |

#### 15.12.3 פלטים
| יעד | נתון |
|---|---|
| לקוח / steganography_service | `FileResponse {id, filename, is_carrier, is_steg_object, ...}` |
| לקוח / steganography_service | זרם בתים של הקובץ בהורדה |
| MinIO | חלקי multipart upload, השלמת העלאה |
| Files DB | INSERT `files` עם is_carrier (נקבע לפי גילוי קודק), UPDATE is_steg_object |

### Steganography Service

#### 15.12.1 תפקיד
הלוגיקה המרכזית של המערכת. מוריד carrier ו-payload מ-files_service, מריץ pipeline של DCT + הטמעה/חילוץ בthread נפרד, ומעלה את התוצאה חזרה. מכיל מספר מודולים פנימיים:

| מודול | תפקיד |
|---|---|
| DCT | המרה בין תחום הפיקסלים לתחום התדרים ובחזרה |
| QIM | הטמעה וחילוץ על מקדם יחיד דרך קוונטיזציה |
| SS / ISS | הטמעה וחילוץ מבוססי מכפלה סקלרית על וקטור יחידה |
| STDM | הטמעה וחילוץ על ה-dot product עם back-projection |
| Reed-Solomon | קידוד ופענוח עם תיקון שגיאות — **TODO** |
| AES | הצפנת payload לפני הטמעה — **TODO** |

#### 15.12.2 קלטים
| מקור | נתון |
|---|---|
| לקוח (דרך gateway) | `POST /embed {carrier_id, payload_id, configs}` |
| לקוח (דרך gateway) | `POST /extract {steg_object_id, configs}` |
| JWT Bearer token | user_id + raw token string (להעברה ל-files_service) |
| files_service | bytes של קובץ carrier (video) |
| files_service | bytes של קובץ payload |
| files_service | bytes של steg object (בחילוץ) |
| Eureka | jwt_public_key, files_service_url |

#### 15.12.3 פלטים
| יעד | נתון |
|---|---|
| files_service | multipart upload של steg object (הטמעה) |
| files_service | multipart upload של payload מחולץ (חילוץ) |
| files_service | `PATCH /internal/files/{id}/embedded` — סימון is_steg_object (הטמעה בלבד) |
| לקוח | `FileResponse` של הקובץ שנוצר |
| לקוח | 400 InsufficientCapacity אם ה-carrier קטן מדי לholds ה-payload |

### 15.12.4 הבהרה — זרימת מידע בין יחידות

קלט יכול להגיע מארבעה מקורות: מהמשתמש (HTTP דרך הדפדפן), מהרשת הפנימית (שירות אחר קורא לשירות זה), מבסיס הנתונים (PostgreSQL), או מאחסון הקבצים (MinIO). פלט יכול לצאת לאותם יעדים.

נקודות מפתח בזרימה:

**טוקן המשתמש עובר דרך שירות הסטגנוגרפיה** — כדי שה-steganography_service יוכל לגשת ל-files_service בשם המשתמש, הוא שולף את הטוקן הגולמי מהבקשה המקורית ומצרף אותו לקריאות שלו ל-files_service. כך files_service רואה את טוקן המשתמש ומאמת את הבעלות על הקבצים.

**אימות JWT מבוזר** — ה-Gateway אינו מאמת JWT. כל שירות מאמת בעצמו את הטוקן מול המפתח הציבורי שקיבל מ-Eureka בזמן אתחול. כך אין תלות חזרה ב-auth_service בכל בקשה.

**גילוי קודק הוא פעולה פנימית ב-files_service** — הלקוח לא צריך לציין אם הקובץ הוא carrier. files_service קובע זאת אוטומטית בסיום ההעלאה על ידי הורדת 2MB ראשונים מ-MinIO ובדיקת הקודק דרך ffmpeg.

**זרימת ה-saga ברישום** — auth_service כותב לשני בסיסי נתונים שונים (user DB דרך user_service, auth DB ישירות). כישלון בשלב השני מפעיל מחיקה מפצה בשלב הראשון, כדי למנוע נתונים יתומים.
