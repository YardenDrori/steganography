# תיעוד פרויקט - פלטפורמת סטגנוגרפיה בווידאו

---

## תיאור הארכיטקטורה

### 11.1 ארכיטקטורה של הפתרון - Top Down

ברמה הגבוהה ביותר, המערכת מורכבת משלוש שכבות. שכבת הלקוח היא ממשק המשתמש הרץ בדפדפן. שכבת השירותים היא אוסף שרתי ה-backend המטפלים בלוגיקה העסקית. שכבת הנתונים היא תשתית האחסון.

תעבורת הלקוח מגיעה תמיד דרך ה-API Gateway, שהוא נקודת הכניסה היחידה של המערכת. ה-Gateway מנתב כל בקשה לשירות המתאים בהתאם לנתיב. השירותים עצמם אינם חשופים ישירות ללקוח ומתקשרים ביניהם באופן פנימי. כל השירותים רשומים בשירות Eureka שמשמש גם כמקור קונפיגורציה. שכבת הנתונים כוללת את PostgreSQL לנתונים רלציוניים ואת MinIO לאחסון קבצים.

---

### 11.2 תיאור הרכיבים בפתרון

**API Gateway - פורט 3000**
ה-Gateway מממש פרוקסי שקוף לחלוטין. הוא קורא בזמן אמת מה-EurekaConfigs את כתובת השירות המתאים לכל נתיב, מסיר את הקידומת /api לפני הניתוב, ומעביר את הבקשה כולה לשירות היעד כולל כל הכותרות וגוף הבקשה. גוף הבקשה מועבר בסטרימינג ישיר ללא בופרינג. ה-Gateway אינו מבצע אימות JWT, הדבר מתבצע בכל שירות באופן עצמאי.

**Auth Service - פורט 3001**
שירות האימות אחראי על מחזור חיי הזהות של המשתמש. סיסמאות נשמרות מגובבות באמצעות Argon2. טוקני JWT נחתמים באמצעות RS256, חתימה אסימטרית מבוססת RSA, מה שמאפשר לכל שירות לאמת טוקנים באמצעות המפתח הציבורי בלבד ללא פנייה חזרה לשירות האימות. בהתחברות מוצלחת מונפקים שני טוקנים: access token לטווח קצר ו-refresh token לטווח ארוך השמור ב-PostgreSQL וניתן לביטול. למשתמשים מוקצים תפקידים (roles) המאפשרים הרשאות שונות.

תהליך ההרשמה מיושם כ-Saga: ראשית נוצר פרופיל המשתמש בשירות המשתמשים, ולאחר מכן מוקצה לו תפקיד ברירת מחדל. אם שלב הקצאת התפקיד נכשל, מופעלת פעולת פיצוי אוטומטית שמוחקת את הפרופיל שנוצר, כדי לשמור על עקביות הנתונים בין השירותים.

**User Service - פורט 3002**
מנהל פרופילי משתמשים הכוללים שם משתמש, שם פרטי ושם משפחה, כתובת מייל, מספר טלפון ומידע נוסף. משתמשים יכולים לעדכן את פרטיהם ישירות. בנוסף לנתיבים הציבוריים, קיים נתיב פנימי לאימות פרטי כניסה שמשמש את שירות האימות בלבד בעת תהליך ההתחברות.

**Steganography Service - פורט 3003**
הרכיב הלוגי המרכזי של המערכת. מעבד וידאו מסגרה-מסגרה ומבצע הטמעת מידע בפיקסלים. מספר פרטי יישום ראויים לציון: העיבוד מתבצע על בלוקים של 4x4 פיקסלים, וה-DCT מוחל על כל בלוק כדי לזהות אילו מקדמים מתאימים להטמעה. 64 הביטים הראשונים של כל הטמעה מוקדשים לכותרת המכילה את גודל המטען, כך שהמחלץ יודע מתי לעצור. השירות מחזיר שגיאה אם המטען גדול מדי להכלה בווידאו הנתון.

ניהול החוטים של שירות זה מתואר בפרק 11.3.

**Files Service - פורט 3004**
מנהל את כל מחזור חיי הקבצים מול MinIO. העלאת קבצים גדולים מיושמת כ-multipart upload בשלושה שלבים: אתחול העלאה, העלאת chunks בנפרד, ואישור סיום. לאחר השלמת ההעלאה, השירות בודק אוטומטית אם הקובץ הוא וידאו תקין על ידי ניתוח ה-codec שלו, ומסמן אותו בהתאם. הקודקים הנתמכים הם H.264, HEVC, VP9, VP8, AV1 ו-MPEG4. כל קובץ מסומן האם הוא steg object, כלומר האם כבר הוטמע בו מידע. עדכון סימון זה מתבצע דרך נתיב פנימי שמשמש את שירות הסטגנוגרפיה בלבד, אשר קורא לו עם סיום ההטמעה כדי לעדכן את סטטוס הקובץ. כל גישה לקובץ עוברת אימות בעלות.

**Eureka Service - פורט 3005**
שירות גילוי וקונפיגורציה. כל שירות נרשם בו בעת אתחול, טוען ממנו את הגדרות הסביבה שלו דרך EurekaConfigs, ומשתמש בו כדי לאתר שירותים אחרים בזמן ריצה.

**Frontend**
אפליקציית React 19 עם TypeScript ו-Tailwind CSS v4. רצה בדפדפן המשתמש ומתקשרת עם ה-API Gateway דרך Axios. כוללת ניהול מצב אימות גלובלי דרך AuthContext ונתיבים מוגנים שמפנים משתמשים לא מחוברים לדף הכניסה.

**ניהול שגיאות ועמידות**

כל פונקציה שעלולה להיכשל מחזירה `Result<T, E>` - סוג המייצג הצלחה עם ערך או כישלון עם שגיאה, או `Option<T>` כשהיעדרות ערך היא מצב לגיטימי ולא כשל (למשל, שאילתת DB שעשויה לא למצוא שורה, או חילוץ refresh token מ-cookie שעשוי להיות נעדר). שניהם מתפשטים אוטומטית במעלה שרשרת הקריאות באמצעות אופרטור ה-`?` - `Option` מומר ל-`Result` עם שגיאה מתאימה ברגע שנדרש טיפול מפורש. לכל שירות יש enum שגיאות ייעודי המממש המרה אוטומטית לתגובת HTTP עם קוד סטטוס מתאים. כך כישלון שאילתת DB עמוק בתוך הלוגיקה העסקית הופך אוטומטית לתגובת שגיאה ללא צורך בטיפול ידני בכל שכבה - אם לא טיפלת בשגיאה, המהדר של Rust פשוט לא יקמפל.

קלט מהמשתמש עובר ולידציה בגבול הכניסה דרך `ValidatedJson` לפני שמגיע לכל לוגיקה עסקית - שגיאות ולידציה נחסמות כאן ומוחזרות כ-400 Bad Request. בתקשורת בין שירותים, כישלון באיתור שירות יעד ב-Eureka או כישלון בקריאת HTTP אליו מתפשט כשגיאה חזרה ללקוח מיד ללא retry - כישלון הוא כישלון. פעולה מורכבת כמו הרשמת משתמש מיושמת כ-Saga עם פעולת פיצוי: אם שלב ביניים נכשל, שלבים שכבר הצליחו מבוטלים אוטומטית כדי למנוע מצב נתונים לא עקבי בין שירותים.

### 11.3 תהליכי מערכת ההפעלה

כל שירות backend רץ כתהליך עצמאי של מערכת ההפעלה. ניהול הבו-זמניות בתוך כל שירות מתבצע באמצעות Tokio, סביבת הריצה האסינכרונית הנפוצה ב-Rust, המאפשרת טיפול בבקשות מרובות במקביל בתוך תהליך יחיד מבלי לחסום חוטים. Tokio מנהל internally thread pool משלו לביצוע משימות ה-async, מה שמייתר את הצורך ביצירה ומחיקה של חוטים לכל בקשה, פעולה יקרה ברמת מערכת ההפעלה.

שירות הסטגנוגרפיה הוא החריג המשמעותי. בניגוד לשאר השירותים שהם IO-bound, עיבוד הווידאו הוא CPU-bound לחלוטין. הרצת עיבוד CPU-bound על ה-async executor של Tokio תחסום את חוטי ה-executor ותמנע ממנו לטפל בבקשות נכנסות אחרות. לכן עיבוד הווידאו מועבר ל-thread pool ייעודי לפעולות blocking שמנוהל בנפרד על ידי Tokio. גם כאן נשמר היתרון של thread pool קיים: במקום ליצור ולהרוס חוט לכל בקשת עיבוד, הבקשה מועברת לחוט פנוי מהמאגר הקיים.

### 11.5 תיאור API בארכיטקטורה

ה-API של המערכת הוא RESTful ומוגש על גבי HTTP. כל הנתיבים עוברים דרך ה-API Gateway ומקובצים לפי תחום אחריות. בקשות לנתיבים המחייבים הזדהות דורשות כותרת Authorization עם Bearer token בפורמט JWT. נתיבי האימות בלבד הם ציבוריים ואינם דורשים טוקן.

קבוצות הנתיבים הן:
- /api/auth/* - הרשמה, התחברות, רענון טוקן
- /api/users/* - ניהול פרופיל משתמש
- /api/files/* - העלאה, הורדה וניהול קבצים
- /api/embed/* - הגשת בקשת הטמעה וקבלת תוצאה
- /api/extract/* - הגשת בקשת חילוץ וקבלת תוצאה

תיעוד מפורט של כל endpoint מופיע בפרק 14.1.

### 11.6 תיאור פרוטוקולי התקשורת

התקשורת בין כל הרכיבים מתבצעת על גבי HTTP עם גוף בקורמט JSON. גילוי השירותים מתבצע דרך ה-REST API הסטנדרטי של Eureka, שכל שירות קורא לו בעת האתחול לצורך רישום ובזמן ריצה לצורך איתור שירותים אחרים. התקשורת הפנימית בין שירותים מתוכננת לעבור לפרוטוקול mTLS לאימות דו-כיווני ברמת התעבורה.
